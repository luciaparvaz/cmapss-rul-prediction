Every number in this document is produced by `train.py` and read directly from
`outputs/final_results.csv` (and the rest of the CSV/JSON files in `outputs/`) — nothing
is typed by hand. If you re-run the pipeline and the numbers change, this README is
stale until it's regenerated.

This is the English translation of the project's Spanish pipeline: same logic, same
formulas, same seeds, same data (`archive/` is shared with the Spanish version — no need
to duplicate ~5.6MB of identical FD001 files). It was executed end to end on this same
machine and reproduces the Spanish numbers to the decimal (aside from negligible
floating-point noise from parallel reduction order, e.g. a Holm t-statistic differing at
the 5th decimal).

## Dataset description

| Parameter | Value |
|---|---|
| Training engines | 100 |

| Failure mode | High-pressure compressor (HPC) degradation |

**Physical sensor identification** (Saxena et al. 2008, Table 2) — s3 (T30) and s4 (T50)
are **temperatures**, not pressures:

| Sensor | Description |
|---|---|
| s2 | T24 — LPC outlet total temperature (°R) |
| s3 | T30 — HPC outlet total temperature (°R) |
| s4 | T50 — LPT outlet total temperature (°R) |
| s7 | P30 — HPC outlet total pressure (psia) |
| s8 / s9 | Nf / Nc — Physical fan / core speed (rpm) |
| s11 | Ps30 — HPC outlet static pressure (psia) |
| s12 | phi — Fuel flow / Ps30 ratio |
| s13 / s14 | NRf / NRc — Corrected fan / core speed (rpm) |
| s15 | BPR — Bypass ratio |
| s17 | htBleed — Bleed enthalpy |
| s20 / s21 | W31 / W32 — HPT / LPT coolant bleed (lbm/s) |

Sensors dropped for near-zero variance (std < 0.01, computed on train): s1, s5, s6, s10,
s16, s18, s19.

## Pipeline (leakage-free)

```
Raw FD001 data
  -> Global MinMaxScaler, FIT ONLY ON TRAIN (14 informative sensors)
  -> Sliding-window features: mean, std, OLS slope (causal/trailing)
  -> Delta (cumulative drift since the engine's first cycle)
  -> Window-size ablation by GroupKFold CV -> window size chosen by CV
  -> s14 ablation (same pipeline in both arms) -> decision by CV
  -> RandomizedSearchCV + GroupKFold(k=5) -> hyperparameters per model
  -> Model selection by out-of-fold CV (never by the test set)
  -> Refit on 100% of train -> ONE single test-set evaluation
```

A prior version of this project normalized each sensor **per engine**, with a
`MinMaxScaler` fit over that engine's **entire** trajectory (test included) — cycle *t*'s
normalized value depended on that same engine's future cycles. Here the scaler is a
single `MinMaxScaler` fit exclusively on train and applied without refitting to test,
verified in code:

```python
global_scaler = MinMaxScaler()
train_df[informative] = global_scaler.fit_transform(train_df[informative])
test_df[informative] = global_scaler.transform(test_df[informative])   # never .fit on test
```

## Feature engineering

For each informative sensor and each window `w` (chosen by CV, see below), `mean`,
`std`, and the OLS slope (`slope`, vectorized via convolution, strictly trailing: cycle
*t* only uses cycles ≤ *t* of the same engine) are computed. A
`delta = value(t) − value(engine's first cycle)` is also added.

### Temporal window ablation (decided by CV, not by hand)

Probe model: LightGBM with fixed, modest hyperparameters, `GroupKFold(k=5)` grouped by
`engine_id`.

| Windows | # features | CV RMSE (± std) |
|---|---|---|
| [15, 30, 50] | 154 | 10.953 ± 0.666 |
| **[30, 50] ★** | **112** | **11.067 ± 0.692** |
| [15, 30, 45] | 154 | 11.148 ± 0.553 |
| [15, 45] | 112 | 11.175 ± 0.663 |
| [15, 30] | 112 | 12.610 ± 1.019 |

**Window chosen by CV:** `[30, 50]` → **112 features** total (14 sensors × 2 windows × 3
statistics + 14 deltas). `[15, 30, 50]` has the lowest mean RMSE, but the difference
(0.11 cycles) is within 1 standard deviation of `[30, 50]`, which uses 42 fewer features
— preferred for parsimony, not because of a demonstrated statistical difference.

### s14 sensor ablation (same pipeline in both arms)

s9 and s14 (physical and corrected core speed) have a Pearson correlation of r≈0.96.
Unlike a prior version of this project — where the "with s14" and "without s14" arms
were trained with different pipelines (features, scaling, and seed) and the decision was
read off the test set — here both arms use exactly the same pipeline and the decision is
made by CV:

| Variant | CV RMSE (± std) |
|---|---|
| With s14 | 11.067 ± 0.692 |
| Without s14 | 11.148 ± 0.695 |

Paired t-test per fold: t=−0.73, p=0.506 → **decision (by CV): keep s14**. The
difference is not significant; unlike a prior version of this project (which dropped
s14 based on a test-set improvement that turned out to be an artifact of comparing two
different pipelines), here it is kept by default in the absence of evidence that
removing it helps.

## Modeling and validation

- **Hyperparameter search:** `RandomizedSearchCV` + `GroupKFold(k=5)` for Ridge,
  RandomForest, XGBoost, and LightGBM (search spaces in
  `src/cmapss/modeling.py`). RandomForest uses fewer combinations (8 vs. 20) because its
  exact-split fitting is ~10-20x slower than the histogram-based models on this dataset
  — a declared compute limitation, not a hidden shortcut.
- **Model selection:** by mean RMSE on out-of-fold predictions (`cross_val_predict`,
  `GroupKFold(k=5)`) with the already-chosen hyperparameters. The test set **plays no
  part** in this decision.
- **Model comparisons:** paired t-test on the mean squared error per engine (aggregated
  from train's OOF predictions, never from the test set), with Holm correction over the
  6 possible comparisons between the 4 models.
- **Test set:** touched **only once**, at the end, to report the metrics of all the
  already-frozen models.

### Final results (single table, `outputs/final_results.csv`)

| Model | CV RMSE (± std) | Test RMSE | Test MAE | Test R² | PHM score |
|---|---|---|---|---|---|
| **LightGBM ★ (chosen by CV)** | **10.824 ± 0.701** | 12.986 | 9.410 | 0.895 | 273.6 |
| RandomForest (CV runner-up) | 10.893 ± 0.627 | **11.855** | **8.574** | **0.912** | **234.2** |
| XGBoost | 10.905 ± 0.635 | 12.552 | 8.752 | 0.902 | 250.3 |
| Ridge | 14.152 ± 1.163 | 14.076 | 11.363 | 0.877 | 298.4 |
| Baseline (mean life − cycles) | — | 36.084 | 26.943 | 0.189 | 21,032 |
| Baseline (train mean) | — | 41.942 | 34.830 | −0.095 | 33,354 |
| Baseline (train median) | — | 49.203 | 38.010 | −0.508 | 166,491 |

**Model chosen by CV:** LightGBM (runner-up: RandomForest, a CV RMSE difference of only
0.07 cycles, not significant — see Holm below).

**Methodological honesty note:** on the test set (touched once), RandomForest gets a
better RMSE than LightGBM (11.86 vs. 12.99). This is exactly the kind of sampling
variation this project's design is meant not to hide: the model was chosen by CV
*before* looking at the test set, and that choice does not change after the fact just
because the test set happened to favor a different model — doing so would be the same
decision leakage a prior audit flagged. The Holm test below shows RandomForest, XGBoost,
and LightGBM are statistically indistinguishable from each other in CV; only Ridge
clearly trails. Given that, the difference observed on the single test set is consistent
with sampling noise among three tied models, not with LightGBM actually being worse.

The three trivial baselines (mean, median, and "train mean life minus cycles observed")
confirm the models learn real signal: LightGBM reduces test RMSE by 64% relative to the
best baseline (36.08 → 12.99); RandomForest, by 67% (36.08 → 11.86).

**Right censoring:** 11 of the 100 test engines have RUL_true ≥ 125 (their true target
was truncated by the cap). The `test_rmse_uncensored` column in
`outputs/final_results.csv` is the RMSE over the uncensored 89% — reported as a **lower
bound**, never as "the real RMSE".

### Statistical comparisons between models (Holm, `outputs/model_comparisons_holm.csv`)

Paired t-test on the mean squared error per engine (OOF-CV). **This is not a
Diebold-Mariano test**: DM requires a single time series with a fixed horizon and a
long-run (HAC) variance; here the comparison unit is 100 distinct engines, a
cross-sectional comparison — a prior version of this project's "Diebold-Mariano" name
was incorrect, as was its Harvey-Leybourne-Newbold correction (applied backwards: it
divided the t-statistic instead of multiplying it).

| Comparison | t | p | p (Holm) | Significant? |
|---|---|---|---|---|
| Ridge vs RandomForest | 8.23 | 7.8e-13 | 3.1e-12 | Yes |
| Ridge vs XGBoost | 8.89 | 2.8e-14 | 1.7e-13 | Yes |
| Ridge vs LightGBM | 8.89 | 2.8e-14 | 1.7e-13 | Yes |
| RandomForest vs XGBoost | 0.82 | 0.416 | 0.832 | No |
| RandomForest vs LightGBM | 1.35 | 0.179 | 0.536 | No |
| XGBoost vs LightGBM | 0.65 | 0.519 | 0.832 | No |

Ridge trails significantly behind the three tree-based models even after Holm correction
over the 6 comparisons. Among RandomForest, XGBoost, and LightGBM there is **no
statistically significant difference** — they are tied within cross-validation noise,
which contextualizes the ranking change on the test set described above.

## Statistical rigor on the residuals

The full true-RUL trajectory is reconstructed for each test engine (fixing a one-cycle
off-by-one error from a prior version of this project: `arange(n_cyc+rul_true,
rul_true, -1)` used to end at `rul_true+1`, not `rul_true`), and predicted cycle by
cycle with the winning model.

**The tests are computed only over `true RUL <= 125`** (n=89 engines; excludes the 11
censored engines and the early portion of each trajectory where `true RUL > 125`). The
reason, visible in `figures/f07_residuals_heteroscedasticity.png` (gray = excluded, blue
= used): the model was trained on the **capped** target at 125, so for cycles with true
RUL well above the cap the prediction is mechanically capped at ~125 while the true-RUL
axis keeps climbing without limit — that produces an almost perfectly linear trend that
is not model heteroscedasticity, it's arithmetic from the cap. Including that segment
(as a prior version of this same pipeline did) artificially inflates the Breusch-Pagan
statistic.

- **Heteroscedasticity (real Breusch-Pagan):** aggregated per engine (n=89, not over the
  ~13,000 individual cycles — a prior version of this project computed what is actually
  a Glejser test with degrees of freedom inflated ×132 by intra-engine
  pseudo-replication). Without filtering by the cap, LM=69.03, p=9.7e-17 seemed to
  indicate strong heteroscedasticity; **filtering to RUL<=125, LM=1.59, p=0.207 — no
  significant evidence of heteroscedasticity.** The "error grows with RUL level" finding
  from a prior version of this README was, for the most part, the cap artifact described
  above, not a real property of the model.
- **Autocorrelation (Ljung-Box, not Durbin-Watson):** on residuals **centered per
  engine** (each engine's mean bias artificially inflated the original DW statistic),
  same RUL<=125 filter. 92.5% of engines show significant autocorrelation (lag=10) —
  unlike heteroscedasticity, this holds after the filter and is an expected result: a
  memoryless tree ensemble on a monotonic degradation trajectory. A sequential model
  (LSTM, TCN) or an autoregressive residual correction could exploit that structure; it
  is out of scope for this project.

## Limitations

- **A single operating condition and a single failure mode** (FD001: sea level, HPC
  degradation). The numbers do not transfer to FD002/FD003/FD004 without retraining;
  that exercise is out of scope for this repository.
- **Target capped at 125 cycles** (piecewise-linear, Heimes 2008): all metrics are
  computed on truncated RUL, not on the real, uncensored RUL.
- **11 censored test engines** (RUL_true ≥ 125): their prediction error is contaminated
  by censoring; reported separately, never hidden.
- **No per-prediction uncertainty quantification** (prediction intervals, conformal
  prediction): the models return a point, not a distribution.
- **Bias direction and safety:** a positive error bias (`true RUL − predicted RUL`, see
  `figures/f07_residuals_heteroscedasticity.png`) means the model predicted **less**
  remaining life than the true value (underestimation, the conservative side). The
  dangerous bias direction in aircraft-engine maintenance is the opposite —
  **overestimating** RUL delays needed maintenance. Any real deployment should
  explicitly monitor and penalize that side of the error (Saxena's PHM metric already
  does, penalizing overestimation with a larger exponential factor).
- **Not suitable for airworthiness decisions**: this is a portfolio exercise on
  simulated NASA data, not a certified system. Any real operational use would require
  additional validation, human oversight, and regulatory compliance.

## Reproducibility

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/Mac:
source .venv/bin/activate

pip install -r requirements.txt
python train.py
```

A single command runs the whole pipeline: loading, CV ablations, hyperparameter search,
final training, test evaluation, statistical block, model saving (with verification that
they reload and reproduce the test RMSE), and figures. On the Spanish version of this
same pipeline (identical code, same seeds, full parallelism `n_jobs=-1`), a real run on
this machine measured **~19 minutes on CPU**, of which ~8.4 min were RandomForest's
hyperparameter search (8 combinations) — by far the slowest step, since it uses exact
splits instead of histograms (see the note in `src/cmapss/modeling.py`) — despite trying
fewer combinations than XGBoost or LightGBM (20 each, both completed in ~4 and ~3
minutes respectively). Total time depends on the machine and on available parallelism;
this English version was itself run end to end and reproduces the same numbers.

**Version compatibility note:** `xgboost` combined with recent `scikit-learn` versions
has a known bug (`AttributeError` in `__sklearn_tags__` when wrapping `XGBRegressor` in
a `sklearn.Pipeline`). `requirements.txt` pins versions where this is already fixed — do
not downgrade `xgboost` without re-checking this.

The XGBoost model is saved in native `models/xgboost_fd001.json` format (stable across
library versions), not as `.pkl`: a prior version's `.pkl` was unrecoverable across
xgboost versions (RMSE≈68 on reload). The other models (Ridge, RandomForest, LightGBM)
are saved with `joblib`.
